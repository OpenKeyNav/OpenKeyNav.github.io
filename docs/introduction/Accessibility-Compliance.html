Accessibility and WCAG Support

Developers can use OpenKeyNav to add keyboard paths to complex web interactions. They must also provide semantic HTML, native controls, accessible names and descriptions, correct state communication, logical focus management, conventional keyboard behavior, and a thorough testing program.

W3C applies WCAG 2.2 conformance to complete pages and processes. Teams must satisfy every applicable success criterion at the claimed level with accessibility-supported technologies.

Where OpenKeyNav can help​

  • Direct target selection: OpenKeyNav displays on-demand labels. Users can select a detected target without moving through every preceding target. Some users may complete dense interfaces with fewer keystrokes.
  • Alternate keyboard interaction: OpenKeyNav provides configured keyboard paths for selection, scrolling, movement, and drag-and-drop.
  • Optional character-key shortcuts: OpenKeyNav keeps its character shortcuts off until a user enables the mode. Users can turn the mode off again. Teams must test site-specific keys for conflicts when they address WCAG 2.2 Success Criterion 2.1.4, Character Key Shortcuts.
  • Developer diagnostics: OpenKeyNav flags elements that its detection rules identify as pointer-clickable and unfocusable. Developers can investigate each flagged element.

Developers must handle the remaining work​

Developers remain responsible for these requirements:

AreaOpenKeyNav's roleWhat developers must verify
2.1.1 KeyboardOpenKeyNav adds an alternate keyboard path for configured targets and actions.Developers verify every state and action through a keyboard interface.
2.1.2 No Keyboard TrapOpenKeyNav lets users exit its modes.Developers verify that focus never becomes trapped.
2.1.4 Character Key ShortcutsOpenKeyNav keeps single-character commands behind an on/off mode and supports configurable keys.Developers keep the off mechanism available and test conflicts with speech input and other commands.
2.4.3 Focus Order and 2.4.7 Focus VisibleOpenKeyNav may move focus during a configured interaction.Developers provide a meaningful order and visible focus.
4.1.2 Name, Role, ValueOpenKeyNav displays shortcut labels for direct selection.Developers provide correct programmatic names, roles, values, and states. Visible OpenKeyNav labels do not supply accessible names.
Drag-and-dropOpenKeyNav provides a keyboard-operated movement path.Developers provide instructions, focus, state, cancellation, and completion feedback. 2.5.7 Dragging Movements also requires a non-dragging single-pointer method unless dragging serves an essential purpose or the user agent controls the functionality.

Developers can use the table to review criteria closely related to OpenKeyNav. Teams must evaluate every applicable WCAG criterion.

Interpreting debug labels​

OpenKeyNav generates debug output with heuristics:

  • OpenKeyNav uses a red label when it detects a pointer-clickable element without keyboard focus. Investigate each red label manually.
  • OpenKeyNav uses a black label when an element matches its keyboard-accessibility heuristic. Developers must still verify semantics, accessible names, focus order, keyboard behavior, state announcements, and visible focus.
  • Custom widgets, delegated event handlers, composite controls, dynamic state, and other application patterns can produce false positives and false negatives.

Confirm every result manually. Prefer fixing the underlying element with native HTML and established widget patterns rather than relying on the shortcut layer as the only means of operation.

Recommended validation​

Before releasing an OpenKeyNav integration:

  1. Complete every task using only the conventional keyboard interface, without first enabling OpenKeyNav.
  2. Repeat the tasks with OpenKeyNav enabled, including activation, cancellation, error recovery, and switching modes.
  3. Check semantics, accessible names, roles, values, states, instructions, focus order, visible focus, and freedom from keyboard traps.
  4. Test shortcut conflicts with the host application, browser, operating system, and assistive technologies. Include speech input when the product support policy covers it.
  5. Test each browser, device, framework, input method, and assistive technology combination in the product's support policy.
  6. Use automated checks to find applicable issues, then perform manual evaluation and usability testing with disabled people. See the W3C's Evaluating Web Accessibility Overview.

Legal scope​

Legislatures, regulators, and procurement bodies set different requirements across jurisdictions, organizations, products, and dates. Organizations must determine which requirements apply to them. Ask qualified counsel to review legal-compliance decisions.
